# 9. Software stack

Three programs and three codecs make a voice turn: the FastAPI backend (`backend/app/*.py`, ~1 300 lines) that transcribes, asks Claude for structured JSON, and optionally speaks; the Expo/React Native companion (`app/src/*.ts(x)`, ~2 000 lines) that owns BLE, the microphones, the headphones and the ring speaker; the Python CLI (`tools/ring-cli`) that stands in for the phone; and `mcring_proto`/`mcring_adpcm`/`mcring_morse`, implemented three times (C, Python, TypeScript) and cross-tested to the byte. This chapter gives a builder who knows *some* programming the fundamentals needed to run, read and extend all of it: FastAPI and async Python, multipart uploads, the Claude API's vision, structured-output, caching and refusal features, speech-to-text and text-to-speech plumbing, React Native with a development client, phone permissions and audio routing, enough TypeScript to read `app/src`, and the testing habits that keep three implementations identical. Read it with `backend/app/main.py`, `backend/app/llm.py`, `app/src/state/useVoiceTurn.ts` and `python/mcring_core/tests/` open.

Every external resource in the "Learn it" tables is linked, and `docs/fundamentals/_links_making.json` records how each link was checked (a search result, or the project's own README, GitHub profile or package-registry metadata). ## 9.1 Python and FastAPI: the shape of the backend

**Why it matters in mcring.** `backend/app/main.py` declares six `/v1` routes (plus a bare `/` that returns the service name, version and endpoint list) with decorators (`@app.post("/v1/ask", response_model=AskResponse, dependencies=[Depends(require_token)])`), takes its inputs as typed parameters (`image: UploadFile | None = File(default=None)`, `mode: str = Form(default="identify")`), returns pydantic models (`schemas.py`: `AskResponse`, `HealthResponse`), gets its configuration through `Depends(get_settings)` from a `pydantic-settings` class that reads `MCRING_*` environment variables and `.env` (`config.py`), and maps provider failures to HTTP codes with one `@app.exception_handler(ProviderError)`. `uvicorn app.main:app --reload --port 8000` runs it; `pytest` runs ~70 backend tests against it (33 of them API tests in `test_api.py`) with every provider faked.

**The concepts.** Python for this codebase is the modern dialect: `from __future__ import annotations`, type hints everywhere (`bytes | None`, `list[dict]`), `@dataclass` for plain records (`LLMResult`, `Transcript`), pydantic `BaseModel` where validation and JSON matter (`LLMAnswer` clamps `confidence` and turns `None` into `""` with `@field_validator`), `functools.lru_cache` for a process-wide singleton (`get_settings`), f-strings, `pathlib`. A **virtual environment** (`python -m venv .venv`) isolates the backend's packages; `requirements.txt` installs `mcring_core` editable from `../python/mcring_core` so the codec code is shared, not copied. **FastAPI** is a thin layer on **Starlette** (routing, requests, responses, test client) and **pydantic** (validation, serialisation, OpenAPI). A route function's parameters *are* its API: FastAPI reads the type and the default (`Form`, `File`, `Query`, `Header`, `Depends`) to decide where each value comes from, validates it, and documents it at `/docs`. `response_model` validates what you return and strips anything not in the schema. **Dependency injection** (`Depends`) is just "call this function first and pass me its result": `require_token` raises `HTTPException(401)` or returns nothing, and declaring it in `dependencies=[...]` attaches it to a route without cluttering the signature. **Exceptions as flow**: `HTTPException(400, "…")` ends the request with that status; the custom `ProviderError(status, retryable)` carries the upstream's status (429/502/503) or 501 for "not configured", and the handler renders `{"detail", "retryable"}` so the app and the CLI can decide whether to retry. **ASGI** is the interface between the server (uvicorn) and the app: an async callable receiving connection events; `--reload` watches files in development, `--host 0.0.0.0` exposes the port on your Wi-Fi so the phone can reach it (`app/README.md`), and the `Dockerfile` builds from the repo root because it needs `python/mcring_core` too. **Settings**: twelve-factor style — everything that differs between your laptop and a server (API keys, provider choice, model names, upload limits) is an environment variable with a typed default, never a constant in code.

## 9.2 Multipart uploads, async versus blocking, and the threadpool

**Why it matters in mcring.** `/v1/ask` is `multipart/form-data`: an optional `image` file (JPEG/PNG/WebP from the ring, ≤ 8 MB, normalised by `images.normalise()` to ≤ 1024 px JPEG), an optional `audio` file (WAV, m4a, mp3, ogg, flac, webm, or raw ring ADPCM sniffed by `audio.sniff_audio()`), and text fields. The handler is `async def` so the upload streams without a worker thread, but every provider call is blocking HTTP or a local model, so STT, LLM and TTS each go through `await run_in_threadpool(...)`; `test_stt_llm_and_tts_run_off_the_event_loop` asserts none of the three ever runs on the loop. `backend/README.md` states the reason: "one slow voice turn does not stall other requests".

**The concepts.** **Multipart/form-data** is the HTTP encoding for forms with files: the body is a sequence of parts separated by a boundary string, each with its own headers (`Content-Disposition: form-data; name="audio"; filename="voice.m4a"`, `Content-Type: audio/mp4`) and raw bytes — no base64, so a 15 KB JPEG costs 15 KB plus a few hundred bytes of headers. React Native's `FormData` accepts `{uri, name, type}` objects and reads the file itself; for raw bytes with no file (the ring-mic clip) `audioPart()` wraps them in a base64 `data:` URI, which RN decodes before sending — a 3 s clip (187 blocks × 132 B ≈ 24.7 KB) becomes ~33 KB of URI in memory, still 24.7 KB on the wire. The server sniffs the real format from the first bytes (`\xff\xd8\xff` for JPEG, `RIFF…WAVE`, 132-byte block structure for ADPCM) rather than trusting the filename. **Async versus blocking**: an `async def` handler runs on one thread's event loop and must only `await`; anything that *blocks* (a synchronous HTTP call to OpenAI or Anthropic, 1–3 s; faster-whisper decoding, hundreds of ms of CPU) freezes every other request for that long. Two fixes: use async clients everywhere, or hand blocking calls to a thread with `run_in_threadpool` (Starlette's wrapper over `anyio.to_thread.run_sync`, default 40 worker threads). The second keeps the simple synchronous provider code and is what the repo does. **The GIL** means Python threads do not run Python bytecode in parallel, but they *do* release the lock while waiting on sockets, so three threads waiting on three provider HTTP calls overlap perfectly; CPU-bound local Whisper is the exception and would need a process pool for real concurrency. **Latency arithmetic** for one turn: BLE clip transfer ~1 s on iOS (ring mic only) + STT 0.5–1 s + Claude 1–3 s + TTS 0.5–1 s, in series, is `docs/04`'s 2–4 s and the N2 budget of 6 s to first spoken word; `latency_ms` in the response measures the server's share. **Limits and errors**: `_read_upload` enforces `max_upload_bytes` (413), `images.normalise` rejects garbage (400), unknown audio is 415, an empty transcript with no photo is 422 — each a distinct, testable status so the client can tell the user something true.

## 9.3 Sessions and conversation memory

**Why it matters in mcring.** "What is this?" → "Is it edible?" works because `sessions.py` keeps, per `session_id`, the last 8 turns (`{question, answer_json}`) and the last photo with its media type, for 30 minutes (`ttl_s=1800`), in a plain dict in the process. `main.py` re-attaches the stored photo when a follow-up arrives without a new one, prefixes the question with `PREVIOUS_PHOTO_NOTE`, and chooses the prompt template with `_effective_mode()` (no photo anywhere → `chat`; a follow-up with a question → `custom`; a photo with no question → `identify`). `llm._history_blocks()` replays the last 6 turns as text, never the old images. The phone stores the id in `sessionRef` and sends it back every turn; the CLI passes `--session`.

**The concepts.** HTTP is stateless; *sessions* are the server's way to remember a client between requests, keyed by an id the client echoes. Where that memory lives decides what the service can do: a **process dict** is simplest and fastest, but it vanishes on restart and is invisible to a second worker process (`uvicorn --workers 2` would make every other follow-up land in an empty session), which is why `backend/README.md` runs one worker; a **shared store** (Redis, a database) survives restarts and scales horizontally at the cost of serialisation and a network hop. **TTL and sweep**: `_sweep()` deletes sessions idle longer than the TTL on every access — a lazy expiry that needs no timer and bounds memory at (active users × 8 turns × a few KB + one photo ≤ ~300 KB). **What to remember** is a product decision disguised as a data structure: the history is kept as the model's own JSON so the next prompt shows Claude what it said in its own schema; the photo is kept so "is it edible?" can see the foxglove again, but only the *latest* photo, so a long session does not grow into a gallery of 15 KB images re-sent each turn. **Session ids** are generated server-side (`uuid4().hex[:16]`) when the client sends none, and returned in every response; the client must store them (a `useRef`, not state, in `useVoiceTurn` — see 9.6). **Privacy**: a session is a transcript of what someone asked and photographed; the 30-minute TTL and the in-memory store are also a retention policy (`docs/01` N4). Moving to Redis would need the same TTL, encryption at rest, and a way to delete on request.

## 9.4 The Claude API as used here: vision input, structured JSON, prompt caching, effort, refusals

**Why it matters in mcring.** `llm.AnthropicProvider.ask()` is one `messages.create` call: `model=claude-opus-5-5` (`config.py`), `max_tokens=4096` ("adaptive thinking shares this budget; a voice answer itself is ~100 tokens"), a `system` block carrying `SYSTEM_PROMPT` with `cache_control: {"type": "ephemeral"}`, the history replayed as alternating user/assistant text, a user turn whose content is an `image` block (`source: {type: "base64", media_type, data}`) followed by a `text` block, and `output_config={"format": {"type": "json_schema", "schema": ANSWER_SCHEMA}, "effort": "medium"}`. With `MCRING_ANTHROPIC_FALLBACKS=1` the call goes through `client.beta.messages.create(betas=["server-side-fallback-2026-07-01"], fallbacks="default", …)`. Afterwards: `stop_reason == "refusal"` → `ModelRefused` → the stock `REFUSAL_ANSWER`; otherwise the first text block is parsed (`_parse_answer` salvages a JSON object from prose if needed) into `LLMAnswer`; `usage.input_tokens/output_tokens` and a `fallback_message` iteration marker fill `LLMResult`. `prompts.py` is written to be *stable* ("no per-request content, so it caches well") and *spoken* (one to three sentences, no lists, numbers as words).

**The concepts.** The Messages API takes a list of turns, each a list of **content blocks** — text, images, documents, tool results — and returns content blocks plus `stop_reason` and `usage`. **Vision**: an image block is base64 (or a URL/file id) with its media type; the model sees pixels, so what you send decides tokens and quality. The vision docs price an image in 28 × 28-pixel *patches*: ⌈width/28⌉ × ⌈height/28⌉ visual tokens — the same rule `docs/fundamentals/05` §5.6 works through. A QVGA ring photo (320 × 240) is 12 × 9 = 108 tokens, VGA (640 × 480) is 23 × 18 = 414, and the `max_image_edge=1024` normaliser caps a phone-sized 4:3 upload (1024 × 768) at 37 × 28 = 1 036 — a voice-only turn sends none. Images beyond a model's long-edge limit (1 568 px on standard-tier models, 2 576 px on Claude 4.7 and later) are downscaled server-side, so there is no benefit in sending more pixels than the question needs; `docs/04`'s "1–1.5 K tokens" budget is conservative. **Structured outputs**: `output_config.format` with a JSON schema makes the response *conform* to the schema (the model cannot emit a stray key or miss a required one), which is why `ANSWER_SCHEMA` sets `additionalProperties: false` and carries **no `minimum`/`maximum`** — numeric bounds are not supported by the constrained decoder, so `LLMAnswer` clamps `confidence` client-side (`test_schema_has_no_morse_field_and_no_numeric_bounds` pins this). It also marks every key `required`, but that rule comes from the *other* consumer: the same dict is sent to OpenAI's strict mode, which insists on it, whereas Anthropic's dialect allows optional properties (it orders them after the required ones and counts them against a complexity limit). One schema for both means "optional" is spelled as an empty string; the salvage path in `_parse_answer` exists for providers and models that return JSON inside prose. **Prompt caching**: the API caches the prefix of a request (tools → system → messages) up to a `cache_control` marker; a later request with a byte-identical prefix pays ~0.1× for the cached part (0.05×, $0.20/MTok, on Opus 5.5) instead of the $4/MTok base, and the write costs 1.25×. The marker on the system prompt caches the ~540-token instruction block for every user; a model-dependent **minimum cacheable length** applies (512 tokens on the newest models, more on some older ones — below it the marker is silently ignored), and `usage.cache_read_input_tokens` is the only proof it works. The per-session history *after* the system prompt changes every turn, so it is not marked — caching it would cost writes without reads. **Effort and thinking**: Opus 5.5 always thinks (adaptive); `effort` (`low`/`medium`/`high`/`xhigh`/`max`) controls how much, and thinking tokens come out of `max_tokens`, hence 4096 for a 100-token answer — `effort: medium` is the backend's latency/quality knob (`MCRING_ANTHROPIC_EFFORT`). **Refusals**: a safety classifier can end a turn with `stop_reason: "refusal"` (HTTP 200, `stop_details.category` says why); with the `fallbacks="default"` beta the API re-runs the request on a substitute model inside the same call and marks it in `usage.iterations`, which `LLMResult.fallback_model` reports. Faces, people and unsafe content are the expected triggers for a camera on a hand (`docs/07` §4). **Errors** come as typed SDK exceptions — `RateLimitError` (429), `APIStatusError` (4xx/5xx), `APIConnectionError` — which the provider maps to `ProviderError(status, retryable)` so the phone can show "wait and retry" versus "fix the key". **Cost of one photo turn** at Opus 5.5 prices: ~108 image + ~40 question + ~700 history + ~540 system (cached, ~$0.0001) ≈ 850 uncached input tokens ≈ $0.0034, plus ~100 output tokens and a few hundred thinking tokens at $20/MTok ≈ $0.004–0.01 — a cent or two per question, dominated by output and thinking, not by the picture.

## 9.5 Speech-to-text and text-to-speech: formats, sample rates, providers

**Why it matters in mcring.** Two mic paths meet in `stt.transcribe()`: the phone records 16 kHz mono AAC in an `.m4a` container (`recorder.ts`, 32 kbit/s), the ring sends raw IMA-ADPCM at 16 kHz in 132-byte blocks that `prepare_audio()` converts to WAV with `mcring_core.adpcm.adpcm_to_wav` before the provider sees it. Providers: OpenAI `gpt-4o-mini-transcribe` (default) or local `faster-whisper` (`base.en`, int8 on CPU, lazily imported, 501 if missing), or `none`. Output: `tts.synthesize()` asks OpenAI `gpt-4o-mini-tts` for mp3 (phone/headphones) or raw 24 kHz PCM, which `audio.resample()` low-passes and decimates to 16 kHz (polyphase FIR with numpy, linear without) and `pcm_to_ring_adpcm()` encodes for the ring speaker; the default `MCRING_TTS_PROVIDER=none` leaves speaking to the phone's own engine (`expo-speech`).

**The concepts.** Digital audio is **PCM**: samples per second (the *sample rate*) of signed integers (16-bit here). Nyquist: a rate f_s captures frequencies below f_s/2, so 16 kHz carries up to 8 kHz — "wideband" speech, fully intelligible (telephones are 8 kHz / 4 kHz bandwidth; music is 44.1/48 kHz). Bit rates: 16 kHz × 16 bit = 256 kbit/s raw; the ring's IMA-ADPCM stores 4 bits per sample — a 132-byte block holds 256 samples (4-byte header + 128 bytes of nibbles) = 16 ms, so 8.25 kB/s ≈ 66 kbit/s, a 3 s clip ≈ 24.7 KB; AAC at 32 kbit/s is 4 KB/s — half of ADPCM for better quality, but it needs a hardware or software encoder the ring does not have. **Containers versus codecs**: `.m4a`/MP4 is a container that here holds AAC; WAV is a container that holds PCM with a 44-byte header (`adpcm.pcm_to_wav`); mp3 and ogg are both; providers decode containers themselves (OpenAI) or through PyAV/ffmpeg libraries (faster-whisper), which is why the server converts only the one format nobody else knows — ring ADPCM — and sniffs the rest. **Resampling** 24 kHz → 16 kHz is a ratio of 3:2: upsample ×2, low-pass below 8 kHz, keep every third sample; skipping the filter aliases 8–12 kHz content down into the speech band as hiss, which is what the polyphase FIR prevents and the linear fallback only approximates. **Speech recognition** models (Whisper and its descendants) take log-mel spectrograms of 16 kHz audio and emit text with a language model's help; `faster-whisper` is a CTranslate2 port that runs the same weights several times faster on CPU at int8; `base.en` (~150 MB) is adequate for short, close-mic questions, `small`/`medium` cost seconds more per clip. **VAD** (`vad_filter=True`) trims silence so a 0.3 s accidental tap transcribes to "" (→ 422) instead of a hallucinated word. **Text-to-speech** engines render text to a waveform; the backend truncates at 1 500 characters, collapses whitespace, and chooses mp3 for the phone (small, universally decodable) or PCM for the ring path because decoding mp3 server-side would need another dependency. **Latency** is the design constraint: STT 0.5–1 s, TTS 0.5–1 s for a two-sentence answer, so the prompt asks for 1–3 sentences and the phone's on-device TTS starts instantly from `speech_text` while the server's voice is an opt-in.

## 9.6 React Native with an Expo development client

**Why it matters in mcring.** The app is "an Expo dev-client / prebuild app, not Expo Go" because `react-native-ble-plx` and `expo-av` need native code (`app/README.md`): `npx expo prebuild` generates `ios/` and `android/` from `app.json`, whose `plugins` array configures the BLE library (background central mode, the permission string) and `expo-av` (the microphone string); `npx expo run:ios` needs a real iPhone because the simulator has no Bluetooth. The UI is two screens; the logic is two hooks — `useRing` (connection, status, events, photos, clips, config sync) and `useVoiceTurn` (the record → ask → transcript → speak state machine with phases `idle | listening | thinking | speaking`) — and a handful of pure modules (`proto.ts`, `audioStream.ts`, `settings.ts`, `morse.ts`) with no React imports so Jest can test them.

**The concepts.** **React** renders a tree of components from state: a component is a function that returns JSX; `useState` holds values whose change should re-render; `useEffect` runs side effects after render (subscribe/unsubscribe); `useCallback`/`useMemo` keep function and object identities stable so children and effects do not re-run needlessly; and **`useRef`** holds a mutable value that does *not* trigger a render — the pattern that dominates `useVoiceTurn`: `settingsRef.current = settings`, `phaseRef`, `busyRef`, `sessionRef`, `startSeq`, because BLE callbacks and timers fire between renders and must read the *latest* value, not the one captured when the closure was created (the stale-closure problem). The rule of thumb in that file: *state for what the screen shows, refs for what the callbacks need*. **React Native** maps components to native views and runs the JS on **Hermes**; anything the OS provides (Bluetooth, audio sessions, the file system) is a **native module** bridged into JS. **Expo** packages the toolchain: the managed project (`app.json`, `expo` SDK 52), the **config plugins** that edit `Info.plist` and `AndroidManifest.xml` at prebuild time so you never hand-edit them, `expo-dev-client` which is Expo Go rebuilt *with your* native modules, and the `expo-*` libraries (`expo-av`, `expo-speech`, `expo-file-system`). **Expo Go** ships a fixed set of native modules; a library outside that set means a development build, which is the whole reason for `prebuild`. **Metro** bundles the JS and serves it to the dev client over Wi-Fi; `expo start --dev-client` is the loop. **Async everywhere**: BLE, recording and `fetch` return promises; `useVoiceTurn` sequences them with `async/await` inside `useCallback`s and guards re-entrancy with `busyRef` and the `startSeq` counter ("a BUTTON_UP that lands during the awaits below is seen by stop/cancel"). **The state machine** is explicit: `startListening(origin)` decides ring mic versus phone mic, starts recording and (phone-mic path) waits ~700 ms to request a photo; `stop` produces an `AskInput`; `runAsk` posts to `/v1/ask`, patches the transcript, cues the ring and calls `speakAnswer`, which fans out to phone TTS/mp3 and/or `streamAudio()` to the ring. Barge-in is a rule of the machine (pressing while `speaking` interrupts; while `thinking` is ignored).

## 9.7 Phone permissions, background modes and audio routing (iOS and Android)

**Why it matters in mcring.** `app.json` declares the whole permission story: iOS `NSBluetoothAlwaysUsageDescription` and `NSMicrophoneUsageDescription` strings, `UIBackgroundModes: ["bluetooth-central", "audio"]`; Android `BLUETOOTH_SCAN`, `BLUETOOTH_CONNECT`, `ACCESS_FINE_LOCATION`, `RECORD_AUDIO`, `MODIFY_AUDIO_SETTINGS`. `recorder.ts` sets the audio session before and after each recording (`allowsRecordingIOS`, `playsInSilentModeIOS`, `staysActiveInBackground`, `DoNotMix`, `shouldDuckAndroid`, `playThroughEarpieceAndroid: false`) and notes "turning it off afterwards puts playback back on the loud route". `speech.ts` plays either `expo-speech` or a server mp3 written to the cache directory through `expo-av`'s `Sound`, and relies on the OS to route to connected Bluetooth headphones. `RingClient.ts` requests MTU 517 and gets 185 on iOS.

**The concepts.** **Runtime permissions**: both platforms require a declared *reason* at build time (the `Info.plist` strings, the manifest entries) and a user grant at run time; a missing declaration crashes the app on first use on iOS and silently fails on Android. Android's BLE permissions changed at API 31 (Android 12): `BLUETOOTH_SCAN`/`BLUETOOTH_CONNECT` replace the old location requirement, but `ACCESS_FINE_LOCATION` is still needed to scan on Android 11 and below — hence both in the manifest and the library's plugin handling the request flow. **Background**: iOS suspends apps in the background unless a background mode justifies work; `bluetooth-central` keeps BLE notifications arriving (the ring's button events while the phone is in a pocket), `audio` keeps playback alive; the system still throttles scanning (filter by service UUID, which `scan()` does). Android has foreground services and vendor-specific battery optimisation that can kill BLE in the background — the Punch Through guides catalogue it. **Audio sessions**: iOS has one `AVAudioSession` per app with a *category* and *options*; recording requires a record-capable category (`allowsRecordingIOS: true` → PlayAndRecord), which changes the Bluetooth route from A2DP (stereo, high quality, output only) to **HFP** (the hands-free profile: mono, 8–16 kHz, with the headset's microphone) — so while the app records through a headset, the headset's mic is used and playback quality drops; switching back (`allowsRecordingIOS: false`) returns to A2DP, the "loud route". `DoNotMix` pauses other apps' audio, `playsInSilentModeIOS` ignores the mute switch, `staysActiveInBackground` keeps the session when the screen locks. Android's equivalents are **audio focus** (`shouldDuckAndroid`: other apps lower their volume) and the output device selection (`playThroughEarpieceAndroid: false` keeps the loudspeaker or headset, not the phone earpiece). **Recording** on both goes through the platform recorder (`MediaRecorder`/`AVAudioRecorder`) configured by `VOICE_RECORDING_OPTIONS`: AAC in MP4, 16 kHz, mono, 32 kbit/s — the sample rate STT models want and the smallest file a 2–8 s question can be. **Playback**: `expo-speech` uses the OS text-to-speech voices (`listVoices()` filters by language prefix), `expo-av` plays the mp3 from a `file://` path because RN has no in-memory audio source; both follow the current route, so Bluetooth headphones get the answer without any BLE code of ours — the architecture of `docs/02` ("the phone is the audio hub") is really an audio-session decision. **MTU on phones**: iOS negotiates ATT MTU itself (185) and ignores requests; Android honours `requestMTU(517)` — `RingClient.connect()` reads what it got and sizes writes (`maxWriteForMtu = mtu − 3`, 1 audio block per write on iOS, 3 on Android).

**Learn it.**

## 9.8 TypeScript enough to read `app/src`

**Why it matters in mcring.** `proto.ts` declares the protocol as `enum`s (`Op`, `Fb`, `Cue`, `Cfg`, `RingEvent`, `Flag`), typed records (`interface Status { … }`, `XferStart`), functions over `Uint8Array`, a class (`TransferAssembler`) and little-endian helpers; `backend.ts` parses untyped JSON with narrowing helpers (`str()`, `num()`, `optStr()`, a type-guard filter `(w): w is string`); `settings.ts` uses string-literal unions (`type MicSource = 'ring' | 'phone'`) and a pure `migrateSettings(raw: unknown)` that validates every field; `RingClient.ts` uses generics (`Promise<Device>`, `Record<string, unknown>`), optional chaining (`dev.name?.startsWith('mcring')`), nullish coalescing (`a.type || 'audio/mp4'`, `o.mode ?? 'chat'`) and the deliberate cast `as unknown as Blob` to feed RN's `FormData`. `npm run typecheck` is `tsc --noEmit`.

**The concepts.** TypeScript is JavaScript with a static type layer that is erased at build time: it catches mismatches before Metro bundles, and it documents intent. **Types versus interfaces**: `interface` for object shapes (`Status`, `AskResult`), `type` for unions and aliases (`type Mode = 'identify' | 'describe' | …`); a string-literal union is the lightweight enum used for settings, while `enum Op { CAPTURE = 0x01, … }` is a real runtime object whose numeric values are the protocol opcodes. **Narrowing** is how you go from `unknown` (JSON from the network, settings from storage) to a type: `typeof v === 'string'`, `Array.isArray(x)`, `v instanceof Uint8Array`, equality against literals (`r.micSource === 'ring' || r.micSource === 'phone'`), and user-defined **type guards** (`(w): w is string => typeof w === 'string'`) that let `filter()` return `string[]`. **`unknown` versus `any`**: `unknown` forces narrowing before use (every parser in `backend.ts` takes `unknown`); `any` turns the checker off, and the repo avoids it. **Generics** parameterise types: `Promise<Device>`, `Record<string, unknown>`, `Omit<Turn, 'id' | 'at'>`, `Partial<Turn>`, `ReturnType<typeof setTimeout>`; **utility types** like `Partial`/`Omit` describe "the same shape minus/optionally these fields" without re-declaring. **Casts** (`as`) assert, never convert: `as unknown as Blob` is a documented lie to satisfy a DOM-typed `FormData.append` with RN's `{uri, name, type}` object — comment such casts, as the code does. **`?.` and `??`**: optional chaining stops at `null`/`undefined`; `??` substitutes only for those two (unlike `||`, which also replaces `0` and `''` — `backend.ts` uses `||` deliberately where an empty string should fall back). **Binary data**: `Uint8Array` is a typed view over an `ArrayBuffer`; `subarray` shares memory, `slice` copies; multi-byte fields are read with explicit little-endian arithmetic (`w[1] | (w[2] << 8)`) or a `DataView` — `protocol/ble-gatt.md` is little-endian throughout, so `unpackStatus` must agree with the C `struct` and the Python `struct.pack("<…")`. **Modules**: `import * as P from '../lib/proto'` namespaces the protocol; `export const`/`export function`; `index`-free relative paths. **Async**: `async`/`await`, `Promise.race` (the AUDIO_DONE timeout in `streamAudio`), `Promise.all` (speak on phone and ring at once), `void somePromise` to mark a deliberately un-awaited call. **Config**: `tsconfig.json` sets strictness (`strict: true` means `null` is a type, implicit `any` is an error); `ts-jest` compiles tests with the same settings.

## 9.9 Testing habits: pytest, Jest, Unity, and the cross-implementation codec tests

**Why it matters in mcring.** The protocol and codecs exist three times and must be byte-identical. `python/mcring_core/tests/conftest.py` compiles the firmware's `mcring_proto.c`, `mcring_adpcm.c` and `mcring_morse.c` into a host CLI with `cc -std=c99 -Wall -Werror` (skipping if no compiler); `test_morse_cross.py` runs it on eight corpora and asserts C units == Python units; `test_adpcm.py::test_c_encoder_matches_python` feeds 2 448 samples of two tones through both encoders and compares bytes; `test_proto.py` pins packet hex (`capture(12, 2) == b"\x01\x0c\x02"`) and `app/__tests__/proto.test.ts` pins the same hex strings in TypeScript; `app/__tests__/fixtures/morse_fixtures.json` is *generated by Python* and checked by Jest; `firmware/ring-esp32s3/test/test_native/test_main.cpp` runs 14 Unity tests on the host (`pio test -e native`), including the CRC-32 check value `0xCBF43926` for `"123456789"` and an ADPCM encode→decode round trip. The backend's tests fake every provider and assert statuses (400/413/415/422/501), threadpool use and refusal mapping; `app/__tests__` cover the pacer, settings migration and backend parsing.

**The concepts.** Tests are cheapest where code is **pure**: `settings.ts`, `proto.ts`, `audioStream.ts` have no React or BLE imports precisely so Jest can run them in Node; `audio.py` and `adpcm.py` have no network. Push I/O to the edges (`RingClient`, the provider classes) and test the middle. **pytest**: a test is a function; **fixtures** (`jpeg_bytes`, `c_tool`, `client`) are declared once with `@pytest.fixture` and injected by name, with scopes (`session` for the compiled C tool so it builds once); **`monkeypatch`** swaps `main.get_provider` for a `FakeProvider` without touching production code; **`parametrize`** turns one test into eight corpora; **`pytest.skip`** keeps the C cross-test honest where there is no compiler instead of silently passing. FastAPI's `TestClient` drives the whole app in-process with real multipart parsing, so a 413 is a real 413. **Jest** with `ts-jest`: `test()`/`expect()`, `describe` loops over fixtures, `toEqual` for deep equality, `Buffer.from(b).toString('hex')` to compare bytes as strings people can read in a diff. **Unity** (via PlatformIO's native environment) is the C world's equivalent: `TEST_ASSERT_EQUAL_UINT8_ARRAY`, `TEST_ASSERT_EQUAL_HEX32`, compiled with the host compiler, no board needed. **Golden values** make three languages agree: write the reference once (Python), freeze its outputs as fixtures or hex literals, and assert the others reproduce them; the CRC-32 check value and the `SOS` unit pattern `[1,1,1,1,1,3,3,1,3,1,3,3,1,1,1,1,1]` are the same kind of constant. **Round-trip and property tests** cover what goldens cannot: encode→decode of a tone must return a signal within 20 dB SNR (`test_roundtrip_snr`), the pacer must never exceed the ring's queue (the `audioStream` tests), a transfer with chunk 3 missing must report `[3]` and refuse to assemble. **Faking the expensive**: `FakeProvider` returns canned `LLMAnswer`s keyed on the question text, `FakeTTS` returns a 440 Hz sine so the ADPCM pipeline can be checked for tone integrity, `fake_stt` returns fixed transcripts — no keys, no network, sub-second runs. **Guarding architecture, not just values**: `test_stt_llm_and_tts_run_off_the_event_loop` asserts *where* code runs; `test_schema_has_no_morse_field_and_no_numeric_bounds` asserts the schema the API will accept; `test_prompt_is_voice_first` greps the prompt. The habit this repo models: when you add a packet, change `mcring_proto.c`, `proto.py` and `proto.ts` together, add the hex literal to all three test files, regenerate any fixture from Python, and run `pytest` (two directories), `npm test` and `pio test -e native` before committing.

**Check yourself.**

1. The Python Morse encoder gets a new rule (treat `'` as a letter gap). Which files and fixtures must change, in which order, and which test fails first if you forget one?
2. `c_tool` has `scope="session"`. What breaks if you change it to the default function scope, and what does `pytest.skip("no C compiler")` protect against?
3. Write a Jest test that pins `P.audioData(7, blocks)` for one 132-byte block of zeros, in the style of `proto.test.ts`. Which bytes come first?
4. `test_roundtrip_snr` asserts > 20 dB for a 440 Hz tone. Why is a golden byte comparison not enough for the ADPCM *decoder*, and why is SNR, not exact equality, the right assertion?

<details><summary>Answers</summary>

1. Change `mcring_core/morse.py` (reference), then `mcring_morse.c` and `app/src/lib/morse.ts`; regenerate `morse_fixtures.json` from Python; update `test_morse.py` expectations. Forget the C change → `test_morse_cross.py` fails on the corpus with `'`; forget the TS change → the Jest `describe('matches the Python reference implementation')` loop fails on the regenerated fixture; forget to regenerate → TS passes against stale fixtures while C fails, a tell that the fixture is out of date.
2. The C sources recompile for every test (eight Morse cases + ADPCM), adding seconds per test and spamming `tmp_path`. The skip makes the cross-implementation suite optional on machines without `cc`, reporting *skipped* rather than passing vacuously or erroring in CI images without a compiler.
3. `test('AUDIO_DATA framing', () => { const blk = new Uint8Array(132); expect(hex(P.audioData(7, blk))).toBe('21' + '0700' + '00'.repeat(132)); });` — opcode `0x21` first, then the little-endian `u16 seq` (7 → `07 00`), then the block: `AUDIO_DATA_HDR_LEN` is 3 in `proto.ts`, matching `floor((MTU − 3 − 3) / 132)` in `protocol/ble-gatt.md`.
4. The decoder has no second implementation to compare against on the Python side (the C decoder runs on the ring), so its correctness is defined by what it reconstructs; ADPCM is lossy, so decoded ≠ original by design — a fidelity bound (20 dB on a mid-level tone) is the specification, and exact equality would fail by construction.
